# OpenLumo v0.1 Design

Date: 2026-11-03
Status: Draft, awaiting review

## 1. Brief

OpenLumo is an open-source, self-hostable AI marketing studio. A user pastes a website URL, OpenLumo learns the brand, plans a month of content, drafts posts, ads, emails and blog articles with matching images, and puts everything on a board where the user approves, edits or regenerates each piece.

The product follows one principle: OpenLumo does the work, the user keeps the veto. Nothing leaves the approval board without an explicit yes.

### Audience

- Founders, solo operators and small teams who want marketing output without an agency.
- Developers who want a polished, hackable, self-hosted alternative to closed AI marketing SaaS products.

### Goals for v0.1

- A public open-source project that runs with `docker compose up`.
- A UI that looks and feels like a polished SaaS product.
- OpenRouter as the single model gateway for text and images, using the user's own API key.
- A provider layer designed so that local models (Ollama, LM Studio, ComfyUI, local TTS) and video and audio generation can be added later without touching domain code.

### Non-goals for v0.1

- Publishing to social networks or email platforms.
- Analytics, performance tracking and the learning loop.
- Autopilot.
- Video and audio pipelines (interfaces exist, nothing is wired).
- Competitor tracking.
- Billing, plans or credits.

### Success criteria

1. A new user can go from an empty instance to an exported, approved post with a branded image in under ten minutes.
2. Brand DNA extracted from a typical small-business website needs only minor edits.
3. Drafts appear on the board without the user writing a prompt.
4. Swapping the model for any capability is a settings change, not a code change.
5. The golden path is covered by an end-to-end test that runs in CI without network access to model providers.

## 2. Prior Art

The concept is inspired by hosted AI marketing platforms such as Holo (tryholo.ai). OpenLumo reuses the publicly described ideas, not their branding, copy, assets or code.

| Concept | Meaning in OpenLumo |
|---|---|
| Brand DNA | Structured, editable profile of a brand's identity, audience, voice and visuals |
| Audit and strategy | One-off document with gaps, content pillars, cadence and campaign ideas |
| Proactive drafts | The planner fills the board without a prompt |
| Workspace | Approval board with approve, edit, regenerate and reject |
| Calendar | Scheduled view of approved content |
| Chat | Conversational assistant over the current brand |
| Credits | Replaced by transparent per-job cost reported by the provider |

Where hosted products stay vague about models, OpenLumo makes every model choice visible and configurable.

## 3. Architecture

### Repository layout

```
openlumo/
├─ apps/
│  ├─ web/                Next.js App Router: UI, server actions, API routes
│  └─ worker/             Node process running pg-boss jobs
├─ packages/
│  ├─ db/                 Drizzle schema and migrations (Postgres)
│  ├─ providers/          Capability-typed model adapters
│  │   └─ openrouter/     First adapter
│  ├─ core/               Domain logic: brand-dna, planner, studio, prompts
│  ├─ storage/            Asset storage: local disk by default, S3-compatible optional
│  └─ ui/                 Design system built on shadcn/ui
└─ docker-compose.yml     web, worker, postgres, optional minio
```

Tooling: pnpm workspaces, Turborepo, TypeScript in strict mode, Tailwind CSS, shadcn/ui, Drizzle ORM, pg-boss, Zod, Better Auth, Vitest, Playwright.

### Rules

- The web app never calls a model directly. Every generation is a job. The worker runs it, stores the result and streams progress to the UI over server-sent events.
- Providers are typed by capability:
  - `LanguageModel`: `complete`, `stream`, `generateObject`
  - `ImageModel`: `generate`
  - `VideoModel` and `AudioModel`: interfaces only in v0.1
- Settings map each capability to a provider and model, for example `brain → openrouter / anthropic/claude-sonnet` and `image → openrouter / openai/gpt-5-image`.
- Domain code in `packages/core` depends only on capability interfaces, never on a concrete provider.
- API keys are entered in the UI, stored encrypted and never sent to the browser. There is no telemetry.

### Users and brands

- Authentication uses Better Auth with email and password.
- The first account on an instance becomes the admin.
- An instance holds many brands. Each brand has its own DNA, strategy, board and calendar.
- Users are invited to brands with the role `owner`, `editor` or `viewer`.

## 4. Domain

### 4.1 Brand DNA

Input is a website URL, or a manual form for brands without a website.

Crawling:

- Fetch the homepage and up to ten same-origin pages, respecting `robots.txt`.
- Extract visible text, meta tags, Open Graph data, logo, favicon and product images.
- Use `fetch` and `cheerio`. No headless browser in v0.1.

Synthesis produces a `BrandDna` object validated by a Zod schema:

- `identity`: name, tagline, offering, products
- `audience`: segments, pain points, buying triggers, objections
- `voice`: tone scales, do and don't lists, sample phrases
- `visuals`: palette from CSS and images, typography hints, image style, logo asset
- `competitors`: entered by the user
- `languages`

Every field is editable on the Brand DNA page.

Feedback in plain language, such as "less corporate, more playful", is stored as a `dna_feedback` entry. Open feedback is included in every later prompt. The user can merge feedback into the DNA, which bumps its version.

### 4.2 Planner

1. The user picks a goal (`awareness`, `leads`, `sales`, `launch`) and the channels they use (Instagram, LinkedIn, X, TikTok, Facebook, email, blog).
2. An audit and strategy job produces a document with strengths, gaps, content pillars, cadence per channel and three to five campaign ideas.
3. A monthly plan job creates content items, each with a channel, format, pillar, angle and date.
4. Every planned item starts a draft job, so drafts are waiting when the user opens the board.
5. A "Plan more" action and an optional weekly schedule keep about two weeks of drafts ahead.

### 4.3 Studio

Each format has its own pipeline and copy schema:

| Format | Copy fields |
|---|---|
| `social_post` | caption, hashtags, image brief |
| `carousel` | slide titles, slide texts, caption, image briefs |
| `static_ad` | headline, primary text, call to action, image brief |
| `email` | subject, preheader, body |
| `blog_post` | SEO title, meta description, outline, article, FAQ |

Pipeline steps:

1. The brain writes the copy and an image brief as structured output.
2. The image model renders the brief.
3. An optional brand overlay composites the logo and headline onto the image using `satori` and `sharp`, because image models render text poorly.

Studio also works on demand: pick a format, add an optional prompt and generate several variants.

### 4.4 Workspace

A board with the columns Suggested, In review, Approved, Scheduled and Exported.

Card actions:

- Approve
- Edit copy inline
- Regenerate copy only, image only, or both, with optional feedback
- Reject with a reason, which is stored as DNA feedback

Only a user can move an item to Approved.

### 4.5 Calendar and export

- Month and week views of scheduled items, with drag to reschedule.
- Export per item or per week: copy to clipboard, download image, ZIP bundle, `.ics` file.
- Emails export as HTML, blog posts as Markdown.

### 4.6 Chat

- A side panel scoped to the current brand.
- Context: Brand DNA, current strategy, recent items.
- Tools: create a draft, regenerate an item.

## 5. Data Model

All brand-scoped tables carry `brand_id`.

| Table | Columns |
|---|---|
| `users`, `sessions`, `accounts` | Managed by Better Auth; `users.role` is `admin` or `member` |
| `brands` | `id`, `name`, `url`, `status` (`crawling`, `ready`, `failed`), `created_by` |
| `brand_members` | `brand_id`, `user_id`, `role` (`owner`, `editor`, `viewer`) |
| `brand_dna` | `brand_id` (one to one), `data` jsonb, `version`, `updated_at` |
| `brand_sources` | `brand_id`, `url`, `kind` (`page`, `image`, `logo`), `text`, `meta` jsonb |
| `dna_feedback` | `brand_id`, `item_id` nullable, `note`, `merged` |
| `strategies` | `brand_id`, `goal`, `channels`, `document` jsonb, `created_at` |
| `content_items` | `brand_id`, `strategy_id` nullable, `channel`, `format`, `pillar`, `angle`, `status`, `scheduled_at`, `current_version_id` |
| `item_versions` | `item_id`, `number`, `copy` jsonb, `image_brief`, `asset_ids`, `feedback`, `author` (`user`, `planner`, `chat`) |
| `assets` | `brand_id`, `kind` (`image`, `logo`, `export`), `storage_key`, `mime_type`, `width`, `height`, `provider`, `model`, `prompt` |
| `job_runs` | `job_id`, `brand_id`, `item_id` nullable, `type`, `status`, `progress`, `error`, `cost_usd` |
| `model_settings` | `capability` (`brain`, `image`, `video`, `audio`), `provider`, `model`, `params` jsonb |
| `secrets` | `name`, `ciphertext`, `iv`, `auth_tag` |
| `chat_messages` | `brand_id`, `user_id`, `role`, `content`, `tool_calls` jsonb |

Decisions:

- Item versions are append-only. Every edit or regeneration adds a row, which gives history and undo.
- Copy is stored as jsonb validated by the schema of its format, so one table holds every format.
- Each job records its cost from the provider's usage data, and the UI shows it.

## 6. Job Flow

```
brand.crawl ──► brand.synthesize-dna ──► brand ready
strategy.create ──► plan.month ──► item.generate × N
item.generate: brain (copy + image brief) ──► image.generate ──► overlay.compose ──► version saved
item.regenerate { scope: copy | image | all, feedback }
export.bundle ──► ZIP or .ics stored as an asset
plan.top-up (weekly, optional)
```

- Concurrency is limited per brand (default 2 parallel generations) and globally.
- The worker updates `job_runs.progress` and sends `pg_notify`. The web app listens and pushes updates to the board over server-sent events, so cards show steps such as "Writing copy" and "Rendering image" live.
- Every job carries its item id and target version number, so retries never create duplicate versions.

## 7. Error Handling

Provider failures become a `ProviderError` with one of these codes:

| Code | Behaviour |
|---|---|
| `rate_limited`, `timeout`, `unavailable` | Retry with exponential backoff, up to three attempts |
| `unauthorized` | Fail fast, link to Settings |
| `content_policy` | Fail fast, offer regeneration with a different angle |
| `invalid_output` | One repair attempt with the validation errors, then fail |

- Partial results are kept. If copy succeeds and the image fails, the version is saved with the copy and the image slot shows the error with a retry action.
- If a site cannot be crawled, the brand falls back to the manual form, prefilled with whatever was collected.
- Stuck jobs expire and are requeued by pg-boss. Idempotency keys prevent duplicates.

## 8. Security

- Secrets are encrypted with AES-256-GCM using a key derived from `APP_SECRET`, and decrypted only on the server or in the worker.
- Brand access is checked in one function, `requireBrandAccess(userId, brandId, role)`, used by every server action and route.
- The crawler resolves DNS before connecting and blocks private, loopback and link-local ranges. It allows only `http` and `https`, limits response size and time, and follows at most ten pages and five redirects.
- Crawled text is passed to models as clearly delimited data, with instructions to treat it as content rather than commands.

## 9. Testing

- Unit tests with Vitest: schemas, prompt builders, palette extraction, overlay composition, encryption, SSRF guard.
- Provider contract tests: one shared suite that every adapter must pass. It runs against a deterministic `FakeProvider` in CI. Live OpenRouter tests run only through `pnpm test:live` with `OPENROUTER_API_KEY` set.
- Integration tests: worker jobs against a real Postgres with the fake provider, covering crawl, DNA, plan, generate, approve and export.
- End-to-end test with Playwright: sign up, add a brand from a local fixture site, see drafts, approve one, export a ZIP. Error card states are covered as well.
- CI on GitHub Actions: lint, typecheck, unit, integration, end-to-end.

## 10. Code Conventions

The codebase should read as if written by a careful human engineer.

- No code comments. Names, types and structure carry the meaning.
- Small modules with one responsibility. A file that grows past a screen or two is a signal to split it.
- Descriptive names for functions, variables and files. Avoid abbreviations except widely known ones (`id`, `url`, `api`).
- Domain types and Zod schemas act as the documentation of data shapes.
- Prefer plain functions and explicit data flow over clever abstractions.
- One way of doing each thing across the codebase: one error type, one access check, one job helper.
- Tests describe behaviour in their names and serve as usage examples.

## 11. Roadmap After v0.1

Each item gets its own spec and plan.

1. Publishing: OAuth connections and native posting for LinkedIn, X, Instagram, Facebook and email providers.
2. Analytics and learning loop: import performance data, report what worked, feed results back into planning.
3. Autopilot: per-channel automatic approval with guardrails.
4. Video and audio: short video ads, voiceover and music through OpenRouter video and speech models.
5. Local providers: Ollama and LM Studio for the brain, ComfyUI for images and video, local TTS for audio.
6. Localisation and competitor tracking.
